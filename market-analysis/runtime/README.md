# Operator-Konfiguration der Analyse-Runtime

Keine Aktivierung durch diese Dateien. Bestehender Start bleibt `npm start` / `node index.js`; keine Änderung einer Railway-Einstellung durch die lokale Integration.

Die normale Routenregistrierung lädt nun die serverseitige Konfiguration. `MARCEL_ANALYSIS_CONFIG_PATH` bezeichnet eine absolute, reguläre JSON-Datei (maximal 2 MB). `production-config.example.json` ist bewusst leer und enthält weder Marktwerte noch Rechte. Die Datei privat bereitstellen und ihren tatsächlichen Pfad konfigurieren. `MARCEL_ANALYSIS_PYTHON_PATH` kann den Interpreterpfad darin überschreiben. Nur absolute Operatorpfade; keine Suche über einen vom Benutzer gelieferten PATH, kein Interpreterparameter aus HTTP.

CPython **3.12.14** ist die lokal geprüfte Referenz. Unterstützungsprüfung: mindestens 3.12, festes JSON-Protokoll 1. Alle Pythonmodule im Verzeichnis `market-analysis/python` verwenden die Standardbibliothek; kein pip, NumPy, Pandas oder zusätzlicher Dienst nötig. Der Interpreter muss einschließlich `ctypes` (Windows) beziehungsweise `resource` (POSIX) vorhanden sein. Die Module werden über den festen eigenen Runner mit `-I -B -X utf8` geladen. Keine Credentials, keine geerbten Provider-Umgebungsvariablen.

Für eine bestehende **Railpack**-Buildkonfiguration kann später regulär ein zusätzliches versioniertes Mise-Paket `python@3.12.14` über `RAILPACK_PACKAGES` bereitgestellt werden. Bestehende zusätzliche Pakete dabei erhalten. Die konkrete vorhandene Builderversion und dessen Pythonverfügbarkeit müssen vor einer freigegebenen Änderung gelesen werden. Die Node-Anwendung bleibt Node-Anwendung; kein Python-Startkommando im Projektroot ergänzen. Den tatsächlich installierten absoluten Interpreterpfad auf dem Ziel feststellen und als `MARCEL_ANALYSIS_PYTHON_PATH` setzen. Keine hier erfundene `/opt/...`-Installation voraussetzen. Offizielle Referenzen: [zusätzliche Pakete](https://railpack.com/guides/installing-packages), [Python-Versionen](https://railpack.com/languages/python), [Node-Start](https://railpack.com/languages/node). Keine dieser Einstellungen wurde produktiv gesetzt.

`calendars` enthält Objekte `{instrumentId, calendar}` mit einem belegten bereits normalisierten Kalender: `from`, `to`, `reference`, optional `zone`, `windows` aus `{id,start,end}`. Keine geratenen Öffnungszeiten; alle Intervalle geordnet, überschneidungsfrei und innerhalb der Abdeckung. Der vorhandene Kalendernormalizer kann zuvor vollständige Tages-/Feiertagsklassifikation in dieses Format überführen.

`specifications`: `{instrumentId, contract, costs, conversion?}` mit den vorhandenen expliziten CFD-/Forex-Kontrakten, Tick-/Pip-/Mengeneinheiten, datierten Quellen, Kosten und gegebenenfalls datierter Währungsumrechnung. Die vorhandene Python-Risikoprüfung validiert diese fachlich erneut; fehlende Werte bleiben blockiert. Keine API-Schlüssel in dieser Datei. Unbekannte Konfigurations-/Grant-/Kontraktfelder werden verweigert.

`authorizations`: vorhandene datierte interne Analyseberechtigung je `instrumentId`, mit `verified`, `usage: internal-analysis`, `reference`, `checkedAt`, `expiresAt`. Das ist kein automatisches Recht für Netzabrufe: separate Daten-/Aktivierungs-Gates der Provider bleiben bestehen. Die Runtime aktiviert keine Quellen und keinen Scheduler.

`GET /api/dashboard/marcel-brain?resource=market-analysis&op=runtime-status` läuft über die vorhandene Dashboard-Anmeldung plus Analyse-Cookie und den internen Backend-Bearer/Session-Assertion. Der Check startet einen begrenzten Probeprozess; er zeigt Version, Speichermechanismus, Konfigurationsanzahlen und Grenzwerte, keine Pfade oder Secrets. `ready`/`interpreterReady` bedeutet erfolgreiche Interpreterprüfung, **keine Freigabe von Datenrechten oder vollständiger Marktabdeckung**. `inputConfigurationReady` ist nur ein struktureller Hinweis; konkrete Instrumentdaten und Gültigkeit werden je Auftrag geprüft.

Fehlende Konfiguration startet keinen Pythonprozess und beschädigt andere Routen nicht. Ungültige Konfiguration sperrt ausschließlich die Analyse mit `ANALYSIS_CONFIGURATION_INVALID`. Neue Analyseaufträge prüfen den Interpreter vor dem Enqueue; Prozessstartfehler bleiben damit ohne verwaiste neue Rechenaufträge. Bereits abgeschlossene Ergebnisse bleiben auch ohne verfügbaren Interpreter lesbar.

Standard 256 MiB harter Python-Speichergrenze (64–512 MiB konfigurierbar), 10 s Wallclock (höchstens 10 s), zusätzlich POSIX-CPUlimit. Windows: Job-Object-Prozessspeicherlimit; POSIX: RLIMIT_AS. Fehlt die Durchsetzung, keine Berechnung. Ein Berechnungsjob global durch bestehende PostgreSQL-Leases; kein neuer Worker. Jeder Prozess hat zusätzlich eine lokale Start-/Busy-Sperre. Probe nur auf ausdrücklichen Aufruf bzw. vor Rechnung, pro Instanz 60 s gecacht; kein Hintergrundpoller. Nach Prozessneustart werden Konfiguration und dauerhafter Jobinput wieder eingelesen.

`mode: offline-fixture` ist ausschließlich für isolierte Tests mit `NODE_ENV=test` und ohne Railway-/Vercel-Deploymentkennung zugelassen. Produktion behält die Fixture-Sperre. Operator-Konfiguration wird nur beim Erzeugen der Runtime geladen; Änderung benötigt einen später freigegebenen regulären Prozessneustart, keinen unkontrollierten Hot-Reload.
